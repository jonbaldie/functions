# Skeleton exploratory pass, 2026-10-29

Base commit: `ec88c46b4b52922e44853ca9545feba9ff02d063` on `origin/master`.

The pass used an isolated worktree, a generated `.key`, PHP 8.5.4, Node 22.22.1, and Yarn 1.22.22. Dependencies came from the committed lockfiles. Composer warned that `composer.lock` is out of date with `composer.json`; dependency freshness was not validated. The normal Composer install failed because locked `phpspec/prophecy` requires PHP below 8.2. A second locked install used `--ignore-platform-req=php`; this is an environment workaround, not validation on the CI version, PHP 8.1. The normal asset build failed with `ERR_OSSL_EVP_UNSUPPORTED`. Setting `NODE_OPTIONS=--openssl-legacy-provider` allowed the build. Both setup limitations are documented in existing [draft PR #25](https://github.com/jonbaldie/functions/pull/25).

`./vendor/bin/phpunit tests --testdox` passed with 42 tests and 126 assertions under PHP 8.5. The pass used an isolated server on `127.0.0.1:39173` with `display_errors=1` to expose errors. The server and port were checked after teardown. The [teardown record](2026-10-29-teardown.txt) records the checks. No containers or browsers were started. No external services or production data were used.

## Journeys

### Start the skeleton and open its welcome page

The README promises an `It works!` page after Composer setup and `php -S`. HTTP `GET /` returned 200 and the expected heading. The documented HTTPS URL failed with a TLS connection error because the PHP server speaks HTTP. The failure recurred after a fresh server start. See [issue #35](https://github.com/jonbaldie/functions/issues/35).

The generated `.key` existed after Composer's autoload script. Repeated HTTP requests served the page with that key. This pass did not test deployment or alternate key management. Existing [issue #21](https://github.com/jonbaldie/functions/issues/21) concerns process environment keys and describes an earlier implementation, so this pass makes no claim about its current status.

### Route requests and serve static files

The ordinary `GET /` returned 200. `GET /missing` returned HTTP 404 and `404 Not Found`. `GET /robots.txt` returned the checked-in file. These results recurred in two runs against each of two fresh server processes.

An unconfigured `POST /` returned HTTP 200 with an undefined-key warning and a fatal `TypeError` from `array_keys()`. `HEAD /` also returned 200 while the server logged a fatal error. The default route table has only `GET`. Both methods failed on repeated requests after a fresh server start. See [issue #33](https://github.com/jonbaldie/functions/issues/33). The status and error disclosure depend on PHP error settings; the underlying exception was observed with `display_errors=1`.

### Build and load frontend assets

`yarn install --frozen-lockfile --non-interactive` succeeded. The ordinary `yarn encore dev` failed on this Node version, while the legacy OpenSSL provider produced three files. All three files returned HTTP 200. The welcome page referenced only `/build/app.js`. The generated `public/build/entrypoints.json` instead listed `/build/runtime.js`, `/build/vendors~app.js`, and `/build/app.js` in that order.

A Node JavaScript context with `window = {}` evaluated `app.js` alone. The module stayed in the `window.webpackJsonp` queue with dependencies on `runtime` and `vendors~app`, rather than executing. This supports [issue #34](https://github.com/jonbaldie/functions/issues/34). A browser was not available, so the pass did not observe a real browser console or test an edited application entrypoint.

The following are representative results from the isolated server. The sequence was repeated with a new server process.

```text

GET /robots.txt        HTTP 200, User-agent: *
GET /build/app.js      HTTP 200
GET /build/runtime.js  HTTP 200
GET /build/vendors~app.js HTTP 200
HTTPS /                curl: (35) TLS connect error
```

The asset comparison and JavaScript probe can be repeated after a successful build:

```sh
php -r 'echo file_get_contents("public/build/entrypoints.json");'
node - <<'NODE'
const vm = require('vm');
const fs = require('fs');
const context = {window: {}};
vm.createContext(context);
vm.runInContext(fs.readFileSync('public/build/app.js', 'utf8'), context);
console.log(context.window.webpackJsonp.length);
console.log(JSON.stringify(context.window.webpackJsonp[0][2]));
NODE
```

The probe printed `1` and `[["./assets/app.js","runtime","vendors~app"]]`. It checks the generated bundle, not browser rendering.
